# docli-cli

Локальное **зеркало только для чтения** ваших пространств [**докли**](https://docli.ru) — для
опытных пользователей, которые работают преимущественно через агентов для работы с кодом
(Claude Code, Codex и другие).

CLI **дополняет MCP-подключение, а не заменяет его**: агент по-прежнему вносит изменения
через MCP-подключение к **докли**, а читает из локальной копии — без отдельного сетевого запроса
на каждое чтение.

- **Зеркало — это кэш, который можно пересоздать.** `docli sync` применяет новые изменения
  с сервера, а `docli sync --full` перестраивает зеркало и удаляет устаревшие файлы. Удалить
  зеркало и синхронизировать его заново безопасно. Локальные правки не поддерживаются: они
  никогда не отправляются на сервер и живут только до полной синхронизации или до следующего
  изменения заметки на сервере — после этого они перезаписываются без конфликтной копии.
- **`docli search` ищет, `docli read` открывает.** Поиск выполняется на сервере — тот же
  BM25-поиск со стеммингом для русского и английского языков, что и в веб-приложении, — и
  печатает для каждой находки серверный путь и идентификатор узла. Для заметки `docli read`
  печатает её содержимое из зеркала, для вложения — метаданные маркера. `docli search` больше не
  выдаёт локальный путь в зеркале для каждой находки: одна команда находит, другая открывает, а
  адрес — тот же, которым оперирует сервер. (`docli doctor` по-прежнему печатает каталоги и
  пути — иначе он не смог бы сообщить о расхождении.)

  **При обновлении с 0.1.4 — несовместимое изменение вывода.** `docli search` больше не печатает
  локальный путь, а в `--json` больше нет поля `local_path`. Передавайте `server_path` находки
  команде `docli read` или её `id` — команде `docli read --id`.
- **Вложения представлены метаданными.** Для вложения `docli read` печатает его ID, MIME-тип,
  размер, хеш SHA-256 и вики-ссылку; сами байты остаются на сервере и загружаются через MCP.
- **`docli doctor`** — трёхсторонняя сверка (сервер / диск / состояние) с классами расхождений.

## Установка

```sh
curl -fsSL https://docli.ru/install.sh | sh        # macOS / Linux
irm https://docli.ru/install.ps1 | iex             # Windows (PowerShell)
```

Вторичный канал: `npx @docli/cli` (npm). Обновление: `docli self-update` (подпись релиза
проверяется ключом, зашитым в бинарник).

> **Язык CLI — английский.** Это инструмент разработчика, а в этом сегменте инструменты
> говорят по-английски: у Yandex Cloud (`yc`) и у самого Timeweb (`twc`) английский CLI и
> русская документация. Побочная выгода — вывод остаётся ASCII и не превращается в кракозябры
> в терминале, который не умеет кириллицу. Русский — язык самого продукта: приложение, сайт и
> эта документация.

## Быстрый старт

```sh
docli init                   # пошаговая настройка: вход, выбор пространства, каталог, агенты
```

Одна команда проводит через всё: если устройство ещё не подключено, `docli init` предложит
войти; дальше вы выбираете пространство из списка (стрелками, никаких ID вручную), каталог
зеркала, конфигурации агентов и то, дописать ли строки в `.gitignore`.

Те же шаги по отдельности — и для скриптов, где вопросов быть не должно:

```sh
docli login                              # вход через браузер по loopback OAuth
docli list                               # все пространства; смонтированные здесь отмечены *
docli init --workspace <id> --dir docli-mirror/notes --gitignore
docli sync                               # разовая синхронизация всех монтирований
docli search "что ищем"                  # серверный поиск по всем монтированиям
docli read "Заметки/план.md"             # напечатать заметку из зеркала (--lines, --id, --json)
docli status                             # вход, монтирования, свежесть зеркал, агенты
docli doctor                             # сверка сервера, диска и состояния
docli logout                             # отключить устройство и удалить учётные данные
```

Файл `docli.toml` нужно коммитить: он только перечисляет пространства по ID, а не по
хэндлам, и не предоставляет доступ.

**Git нужен не всем.** Если проект — не репозиторий git, никаких требований к `.gitignore` нет
и всё работает как есть. Проверка включается ровно тогда, когда зеркало оказывается внутри
рабочего каталога git: там каталоги зеркал и `.docli/` обязаны быть в `.gitignore`, иначе
`docli sync` откажется работать — одно `git add -A` отправило бы чужие заметки в удалённый
репозиторий. Дописать нужные строки можно самим CLI: `docli init --gitignore` (в пошаговом
режиме об этом спрашивают).

## Интерактивно и не интерактивно

Каждая команда работает в обоих режимах. Вопросы задаются, только когда терминал
интерактивен; в конвейере, в CI и с флагом `--no-input` CLI не спрашивает ничего, а если для
продолжения нужен ответ — говорит, какой флаг его заменяет (например, `docli uninstall --yes`).

| Флаг | Что делает |
| --- | --- |
| `--no-input` | Ничего не спрашивать (для скриптов и CI) |
| `-q`, `--quiet` | Без пояснений и хода работы; ошибки и результат остаются |
| `--no-color` | Без цвета; то же делают `NO_COLOR`, `TERM=dumb` и вывод не в терминал |
| `--json` | Машинный вывод у `list`, `status`, `search`, `read`, `doctor` |

Потоки разделены: результат идёт в stdout, ход работы — в stderr. Поэтому
`docli read … | head`, `docli status --json | jq` и `docli sync 2>/dev/null` ведут себя
предсказуемо. Там, где результат команды — это весь её экран (`search`, `status`, `list`, `doctor` в
человекочитаемом виде), предупреждения идут в stdout вместе с ним: `docli status > file`, потерявший
половину экрана, был бы хуже, чем отсутствие перенаправления. `docli read` устроен иначе: результат —
это сама заметка, поэтому stdout принадлежит ей одной, а все оговорки уходят в stderr. При `--json`
в stdout не попадает ничего, кроме JSON.

`docli read` завершается с кодом **3**, когда ни одно выбранное монтирование не содержит
запрошенного, — отдельный код, чтобы скрипт отличал «этого нет в локальном зеркале» от сбоя.
О наличии заметки на сервере он не говорит ничего: установить, что заметки не существует, можно
только по результату `docli search`, в котором индекс не помечен как неполный.

## Удаление

```sh
docli uninstall              # удаляет бинарник и ~/.docli, сначала отключив устройство
docli uninstall --purge      # заодно удаляет зеркала и .docli/ текущего проекта
```

Что удаляется, показывается списком до подтверждения. Без `--purge` файлы проекта остаются
на месте: зеркало пересоздаётся, но лежит в вашем репозитории, и решать его судьбу вам.
`docli.toml` и настройки агентов CLI не трогает никогда.

## Подключение агентов для работы с кодом

`docli init` устанавливает контракт зеркала в `.agents/skills/docli-mirror/SKILL.md` — по
стандартному пути из открытой спецификации Agent Skills; оттуда его читает Codex (порядок
поиска описан в его документации). **Claude Code этот путь не читает** — он читает
`.claude/skills/`, поэтому контракт копируется и туда, вместе с масками `paths:`, выведенными
из вашей таблицы монтирования: тогда он подгружается сам, как только агент работает с файлом
зеркала. Агенты со своим каталогом навыков (Qwen, Cline, Trae) получают свою копию.
`--skills none` отключает это, `--skills claude,codex,…` задаёт список.

### Где кончается гарантия

Контракт — это документ, а документ помогает только после того, как агент его прочитал. Для двух
агентов, у которых есть механизм хуков — **Claude Code и Codex** — `docli init --hooks auto`
устанавливает два хука:

- `PreToolUse` **отклоняет** запись в зеркало и называет в отказе правильную альтернативу;
- `SessionStart` сам, без запроса, сообщает в сессию, насколько зеркало свежее.

Без явной просьбы они не появятся: в пошаговом режиме этот пункт предлагается неотмеченным, а
при `--no-input` их пишет только флаг `--hooks`. Оба агента к тому же спрашивают доверие к
проекту прежде, чем запустить любой локальный хук.

Два ограничения, названные прямо. **Запись через шелл не покрыта** — `sed -i` или `>` в каталог
зеркала пройдут у обоих агентов: чтобы понять, куда пишет строка команды, пришлось бы разбирать
шелл. И **у остальных агентов принуждения нет вовсе**: для них зеркало помечено только для
чтения, а контракт просит не редактировать его — это совет, а не гарантия. `docli status`
показывает, установлены ли хуки в этом проекте и находится ли ещё бинарник, который в них назван.

`docli init --instructions` дополнительно записывает короткий раздел про **докли** в `AGENTS.md`
(его читают Codex, Cursor, Gemini CLI, Zed, Copilot и ещё десятка полтора инструментов) и —
**только если `CLAUDE.md` ещё нет** — создаёт его со строкой `@AGENTS.md`. Существующий
`CLAUDE.md` не правится никогда: строку для вставки CLI просто печатает.

Кроме того, **только по вашему запросу** `docli init` может добавить MCP-подключение этого
проекта к **докли** в конфигурации агентов. В пошаговом режиме это отдельный шаг со списком:
найденные здесь конфигурации отмечены заранее, но записываются только те, что остались
отмеченными. Без вопросов — `docli init --mcp auto` (найденные агенты) или
`--mcp claude,codex,…` (список). Созданная
запись docli содержит URL и необходимые конкретному клиенту параметры транспорта, но не
содержит токена или других учётных данных: при первом подключении каждый агент
самостоятельно проходит OAuth-авторизацию в браузере, и добавленную запись docli безопасно
коммитить. URL содержит метку подключения проекта, которая сохраняется как `mcp_label` в `docli.toml`.
Параметр `--mcp-label` задаёт собственную метку, а `--mcp-bare` использует URL `…/api/mcp`
без метки — для клиентов, которые не передают параметр RFC 8707 `resource`. Если
конфигурацию агента нельзя безопасно изменить автоматически, CLI печатает фрагмент для
ручной вставки.
